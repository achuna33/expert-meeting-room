# 会议流程协议

## 设计原则

**否决权留在最后，红线发现要前移。** 避免「讨论设计半天，最后一票否决」：

- 沃格尔设**两道低成本闸门**（立项 + 粗方案），方向错误尽早停止
- 施奈尔、林纳斯在细设计前做**粗判**（威胁草图 + T-shirt 估算）
- 细设计（福勒完整架构）仅对通过粗方案闸门的方向展开
- 终审否决应极少出现；若出现，须说明「为何前序阶段未拦住」
- 方案定稿前由费瑟斯做**影响面复查**：联动修改无遗漏才交付开工
- **按需参会**：主持人须先深度解析诉求，再按 [meeting-router.md](meeting-router.md) 生成编排方案；跳过须对照真实问题写明理由

## 智能编排（Meeting Router）

完整规则见 **[meeting-router.md](meeting-router.md)**。要点：

1. 深度解析诉求 → 「诉求简报」（真实问题 / 隐含领域 / 工作假设）
2. 基于简报分类（`greenfield` / `change` / `strategy` / …），禁止只扫关键词
3. 选流程模板 T1–T7 → 按入选规则裁剪专家
4. 输出编排方案 → 再执行会议
5. 用户可要求增删专家，更新编排后执行

## 红线清单

议题输入时填写，沃格尔在**立项闸门**确认或补充。会议全程每位专家须对照红线表。

模板见 [red-lines-template.md](red-lines-template.md)。

典型红线项：

- 预算 / 人力 / 上线日期硬约束
- 合规等级（等保、GDPR、个保法等）
- 禁止方案（如明文存密码、无审计日志上线）
- 必须满足的非功能要求（可用性、多租户等）

**触碰红线**：该专家输出 ❌，并在「⚠️ CTO 风险预警」中说明；不得留到终审才首次暴露。

## 输出可读性规范

所有专家发言遵循统一规范：

1. **结论先行**：第一行「核心判断」— 状态标记 + 一句话理由
2. **📌 速览表**：5 行以内最关键结论
3. **表格优先**：枚举内容一律用表格
4. **统一状态标记**：
   - ✅ 通过/可行 · ⚠️ 有条件/待澄清 · ❌ 不通过/不可行
   - 🔴 阻塞 · 🟡 跟进 · 🟢 记录
   - P0 / P1 / P2
5. **红线对照**：每位专家（沃格尔闸门除外）须填「红线对照」表
6. **⚠️ CTO 风险预警**：每位专家（沃格尔除外）须填 — 沃格尔最可能否决的原因 + 建议前置处理
7. **🔗 交接**：写明交给下一位专家的输入
8. **不重复共识**：后发言者对已共识内容仅标 ✅

## 议题输入要求

- **背景** / **目标** / **约束** / **已知信息**
- **红线清单**：至少 3 条不可协商项（见模板）

## 各阶段规则

### 0. 产品战略定向（马蒂·卡根 · `marty-cagan`）

议题 + 红线输入后 invoke，**在立项闸门前**完成宏观方向判断。

输出：战略建议 ▶️ 推进 / 🔽 收窄 / ⏹️ 停止（战略层）

- **⏹️ 停止**：战略上不 worth doing，建议会议结束
- **🔽 收窄**：机会存在但范围或假设需收窄，列出 strategic Won't
- **▶️ 推进**：进入沃格尔立项闸门，交接 Outcome 与战略边界

### 1. 立项闸门（沃格尔 · `werner-vogels` 立项模式）

卡根 ▶️ 推进后 invoke，综合战略输入与约束判断。**禁止**在未通过立项闸门时进入阶段 A。

输出：▶️ 继续 / 🔽 收窄 / ⏹️ 停止

- **⏹️ 停止**：方向与战略/约束冲突，会议结束，不进入阶段 A
- **🔽 收窄**：范围过大，列出必须缩小的项，诺曼在收窄后的范围内重新发言
- **▶️ 继续**：进入阶段 A

### 2. 阶段 A · 粗判

顺序：**唐·诺曼 → 罗恩·科哈维（轻量度量） → 布鲁斯·施奈尔（轻量） → 林纳斯（T-shirt） → 沃格尔粗方案闸门**

| 专家 | 模式 | 产出 |
|------|------|------|
| 唐·诺曼 | 阶段 A | MVP 范围、MoSCoW、不做清单 |
| 罗恩·科哈维 | 轻量度量 | 指标草案、可测性、实验可行性粗判 |
| 布鲁斯·施奈尔 | 轻量威胁草图 | 资产/攻击面/潜在 Blocker 预判 |
| 林纳斯·托瓦兹 | T-shirt 估算 | S/M/L/XL + 关键风险，非人天明细 |
| 沃格尔 | 粗方案闸门 | ▶️进入细设计 / 🔽收窄 / ⏹️停止 |

**粗方案闸门 ⏹️/🔽**：成本极低，禁止已进入阶段 B 才回头改方向。

### 3. 阶段 B · 细设计

仅粗方案闸门 **▶️ 进入细设计** 后 invoke。

顺序：**马丁·福勒 → 林纳斯（明细） → 罗恩·科哈维（完整度量） → 布鲁斯·施奈尔（完整） → Charity Majors（运维） → 交叉讨论 → 沃格尔终审**

| 专家 | 模式 | 产出 |
|------|------|------|
| 马丁·福勒 | 完整架构 | 模块、选型、Trade-off、NFR |
| 林纳斯·托瓦兹 | 人天明细 | 按模块人天、里程碑、CI/CD |
| 罗恩·科哈维 | 完整度量 | 指标表、实验设计、埋点需求 |
| 布鲁斯·施奈尔 | 完整安全审查 | STRIDE、Blocker、合规、验收 |
| Charity Majors | 运维审查 | SLI/SLO、可观测性、on-call、发布回滚 |
| 沃格尔 | 终审 | ✅ / ⚠️ / ❌ |

### 4. 交叉讨论（可选）

- 两位及以上专家冲突
- 施奈尔 Blocker vs 林纳斯成本
- 福勒架构 vs 诺曼 MVP 范围

规则：只讨论分歧点，每人最多一轮补充；仍无法一致时沃格尔裁决。

### 5. 终审与否决

沃格尔输出 **✅ 通过 / ⚠️ 有条件通过 / ❌ 否决**。

**否决使用原则**：

1. 优先 ⚠️ 有条件通过 + P0 修复项，而非 ❌ 否决
2. ❌ 否决须说明类别 + 具体理由 + **为何前序阶段未拦住**（流程缺陷则改流程）
3. 否决须指定**最小退回点**（只回施奈尔改安全，不必从诺曼重来）
4. 修改完成后重新提交**终审**（不必重走已通过的阶段 A/B 环节）

### 6. 详细设计与交付（终审 ✅/⚠️ 后）

终审通过后，会议的最终产出是一份**可直接开工的《开发设计方案》**（单一 `.md` 文件，骨架见 [templates/dev-design.md](../templates/dev-design.md)）：

| 步骤 | 负责 | 产出 |
|------|------|------|
| 1 | 马丁·福勒（`@martin-fowler` 详细设计模式） | 系统设计章节：接口契约到字段、数据模型、关键时序、ADR |
| 2 | 林纳斯·托瓦兹（`@linus-torvalds` 详细设计模式） | 实施计划章节：ticket 级任务拆解、里程碑、DoD、测试计划、发布方案 |
| 3 | 组装 | 概述与需求 ← 诺曼；度量 ← 科哈维；安全 ← 施奈尔；运维 ← 梅杰斯；合并为单一文件 |
| 4 | 迈克尔·费瑟斯（`@michael-feathers` 影响面复查） | 分级影响清单、遗漏比对与退回建议、回归测试范围；✅ 后方案定稿交付 |

规则：

- ⚠️ 有条件通过时，前置条件写入方案的「决议信息」与「风险登记」，相关任务标 P0
- 施奈尔的 Blocker 修复方案必须落实到具体模块与接口（安全设计章节）
- 细化后的工作量超出阶段 B 估算时，须在方案中标注偏差与原因
- **影响面复查不通过时**：遗漏项退回福勒（系统设计）或林纳斯（任务拆解）补入方案后复查，直至 ✅ 才定稿交付；复查结果记入方案「影响面复查」章节

## 结论输出

1. **决议速览**：结论、闸门历史、行动项数、风险数
2. **专家意见汇总表**（含阶段 A/B 各轮）
3. **关键分歧与处理**
4. **行动项清单**
5. **风险登记表**
6. **各专家完整意见**（附于文末）
7. **《开发设计方案》**：终审 ✅/⚠️ 通过时的最终交付物（见「详细设计与交付」阶段）
