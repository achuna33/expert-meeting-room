# 会议智能编排（Meeting Router）

主持人（`start-meeting`）在 invoke 任何专家**之前**，必须先深度解析用户想法，再生成「会议编排方案」，再按方案执行。禁止无脑全员出场，禁止只凭关键词匹配专家。

> 注意：`start-meeting` Skill 内嵌了本规则的精简版（安装后自包含可用）。**修改本文件后，须同步更新 Skill 内嵌版并重跑 `./install.sh`。**

## 编排原则

1. **先理解再选人**：先产出「诉求简报」（真实问题 + 隐含领域），再分类裁剪专家
2. **按需参会**：只邀请与**真实问题**相关的专家；跳过须写明理由（对照简报，而非原文有没有某词）
3. **闸门不可省**：凡走完整决策链，沃格尔三道闸门（立项 / 粗方案 / 终审）保留；轻量会议至少保留**终审**
4. **顺序不可乱**：已入选专家仍按 `meeting-protocol.md` 的阶段顺序排列
5. **用户可覆盖**：编排方案输出后，用户要求「加上某某专家」须采纳

## 诉求深挖（选人前）

从用户原话推断，缺信息标「工作假设」，不追问阻塞：

| 项 | 要回答的问题 |
|----|----------------|
| 表面诉求 | 用户字面要什么 |
| 真实问题 | 为谁、在什么场景、解决什么摩擦；可与表面诉求不同 |
| 成功长什么样 | 可观察结果，不是功能清单 |
| 隐含领域 | 真实问题会碰到的领域；**原文未出现「安全/架构/…」也必须记入** |
| 工作假设 | 补上的背景、目标、约束 |

**选人依据** = 真实问题 + 隐含领域。例：「加个登录」未提安全 → 施奈尔仍应入选。

议题分类与流程模板用简报判断，不用原话关键词计数。

## 议题分类（基于简报分类，再选人）

| 类型 ID | 名称 | 识别信号（满足任一即可倾向） |
|---------|------|------------------------------|
| `greenfield` | 新功能 / 新系统 | 新做、从零、MVP、上线新模块、没有现有实现 |
| `change` | 改动 / 重构 / 迁移 | 改、重构、迁移、替换、升级、影响面、联动、现有系统 |
| `strategy` | 战略 / 方向决策 | 要不要做、值不值得、方向、优先级、战略、路线图 |
| `security` | 安全专项 | 安全审查、渗透、合规、等保、漏洞、认证授权专项 |
| `architecture` | 架构专项 | 架构设计、技术选型、拆分、微服务、性能架构 |
| `ops` | 运维 / 可靠性 | SLO、告警、on-call、可观测性、容量、故障、稳定性 |
| `metrics` | 度量 / 实验 | A/B、指标、转化率、怎么证明有效、实验设计 |
| `estimate` | 排期 / 工作量 | 多少人天、工期、能不能做、排期评估 |
| `minimal` | 极小事项 | 改文案、改配置、一行修复、纯文档（<半人天） |

**主类型**：命中信号最多的类型；**次类型**：可叠加（如 `change` + `security`）。

## 专家入选规则

| Skill | 专家 | 默认 | 入选条件 | 常跳过条件 |
|-------|------|------|----------|------------|
| `marty-cagan` | 卡根 | 新功能 | `greenfield` / `strategy`；或涉及方向取舍 | `change` 且范围明确；`minimal`；纯技术估期 |
| `don-norman` | 诺曼 | 新功能 | 涉及用户功能、体验、需求、MVP | 纯架构/纯运维/纯安全专项；`minimal` 技术改动 |
| `ron-kohavi` | 科哈维 | 新功能 | 涉及 Outcome 验证、增长、转化、A/B、`metrics` | 纯后端重构无指标变化；`minimal`；用户明确不验证 |
| `bruce-schneier` | 施奈尔 | 有条件 | 用户数据、认证、支付、API 对外、合规、隐私、`security` | 纯内部工具无敏感数据；纯架构不改安全边界 |
| `linus-torvalds` | 林纳斯 | 大多数 | 需要交付、排期、实现评估（非 `strategy` 专项） | 纯 `strategy` 且不做实现；`minimal` 可仅 T-shirt 或跳过 |
| `martin-fowler` | 福勒 | 新功能 | 新模块、架构变更、技术选型、`architecture` | 不改结构的小改动；纯度量/纯运维专项 |
| `charity-majors` | 梅杰斯 | 有条件 | 新服务上线、生产变更、SLO、`ops`、高可用 | 纯设计阶段且不上线；`minimal`；无生产影响 |
| `michael-feathers` | 费瑟斯 | 改动 | **`change` 必选**；迁移、重构、改接口/数据模型 | 全新独立代码库且无任何既有调用方/集成方（唯一例外，跳过须在编排方案写明理由） |
| `werner-vogels` | 沃格尔 | **必选** | 任何多专家会议 | 无（至少终审模式） |

### 阶段 C（详细设计 + 影响面复查）

| 交付 | 条件 |
|------|------|
| 《开发设计方案》完整版 | 终审 ✅/⚠️ 且（`greenfield` 或 `change` 且需开工） |
| 轻量结论（无完整方案） | `strategy` 专项、`minimal`、或用户只要决策不要方案 |
| 费瑟斯复查 | 产出《开发设计方案》时**必选**；`change` 类型必选。唯一例外：全新独立代码库且无任何既有调用方/集成方（跳过须写明理由） |

## 流程模板

### T1 · 标准新功能（默认）

```
卡根(战略) → 沃格尔(立项) → 诺曼 → 科哈维(轻) → 施奈尔(轻) → 林纳斯(T-shirt)
→ 沃格尔(粗方案) → 福勒 → 林纳斯(明细) → 科哈维(完整) → 施奈尔(完整) → 梅杰斯
→ [交叉讨论] → 沃格尔(终审) → [阶段C: 福勒+林纳斯+费瑟斯]
```

**跳过示例**：内部工具无 PII → 跳过施奈尔；不上生产只出原型 → 跳过梅杰斯。

### T2 · 改动 / 重构 / 迁移

```
[卡根 可选] → 沃格尔(立项) → 诺曼(轻) → 费瑟斯(影响面预判-可选轻量)
→ 林纳斯(T-shirt) → 沃格尔(粗方案) → 福勒 → 林纳斯(明细) → 施奈尔(若触安全)
→ [梅杰斯 若涉生产] → 沃格尔(终审) → 阶段C(福勒+林纳斯+费瑟斯必选)
```

**重点**：费瑟斯在 `change` 类型几乎必选；科哈维仅当指标/行为变化时加入。

### T3 · 战略决策

```
卡根 → 沃格尔(立项) → [诺曼 若需 MVP 边界] → 沃格尔(终审)
```

无阶段 B/C，交付「战略结论备忘录」而非《开发设计方案》。

### T4 · 安全专项

```
沃格尔(立项) → 施奈尔(轻) → 诺曼(若涉产品) → 福勒(若涉架构) → 林纳斯(修复工作量)
→ 施奈尔(完整) → 沃格尔(终审)
```

### T5 · 架构专项

```
沃格尔(立项) → 诺曼(轻) → 福勒 → 林纳斯 → 施奈尔(若对外/数据) → 梅杰斯(若涉部署)
→ 沃格尔(终审) → 阶段C(福勒详细设计)
```

### T6 · 运维 / 可靠性专项

```
沃格尔(立项) → 梅杰斯 → 福勒(若需架构调整) → 林纳斯(实施) → 科哈维(若改 SLI 与业务指标)
→ 沃格尔(终审)
```

### T7 · 极小事项（minimal）

```
林纳斯(T-shirt) → 沃格尔(终审) → [费瑟斯 若仍有代码改动]
```

跳过卡根、诺曼、福勒（除非用户描述涉及架构）。

**用户确认**：默认编排后立即执行；若用户说「加上/去掉某专家」，更新方案后再执行。

## 快速决策树

```
1. 是否「要不要做/方向」为主？ → T3 战略
2. 是否主要是「改现有」？ → T2 改动（+费瑟斯）
3. 是否 minimal（<半人天）？ → T7 极小
4. 是否安全专项？ → T4
5. 是否架构专项？ → T5
6. 是否运维专项？ → T6
7. 否则 → T1 标准新功能（按入选规则裁剪）
```
